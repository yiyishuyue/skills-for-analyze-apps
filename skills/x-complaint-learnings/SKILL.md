# X 吐槽点与竞品借鉴点（初筛报告）

把社交平台上的**用户原话**整理成可上会的产品证据包：吐槽簇 → 迁移路径 → 竞品对照 → P0–P3 动作。方法源自「懂球帝 · 小红书用户吐槽与竞品借鉴」体例，默认平台是 **X（Twitter）**；用户指定其它平台时，换取数工具、**报告骨架不变**。

## 核心信念

> **吐槽报告的价值不在词云，在于「原话可引用 + 证据有强弱 + 有人真的走了 + 动作能排期」。**

三条不可破：
1. **原话照抄，禁止改写、翻译后当原话、或编造引用。** 每条尽量带可点开的帖文 URL。
2. **先做声量验证。** 若分析主体在该平台几乎没有产品向讨论，写明「原问题不成立」，改做品类矩阵或以主体为「借鉴接收方」——**不要硬凑吐槽簇**。
3. **不确定就标不确定。** 定性初筛 ≠ 抽样调查；禁止写「X% 用户讨厌…」。

## Step 0 · 对齐范围（缺一就问清再搜）

向用户确认或从上下文推断：

| 项 | 说明 |
|----|------|
| 分析主体 | 单品 / 品类矩阵（含主体） / 对照品 |
| 竞品名单 | 用户给出；否则用公开信息初筛并标明 |
| 时间窗 | 默认近 90 天；可对齐用户附件窗 |
| 语言 | 默认英文；若西/葡等密度高，单开短节 |
| 交付形态 | Markdown 初筛 / 一页评审摘要 / PDF |

用户说「需要我提供什么直说」时：直接列出上表缺项，可附 3–5 条已搜到的强信号预览帮其拍板。

## Step 1 · 声量验证（决定报告主语）

1. 用精确产品名、官方 `@handle`、`app`/`ads`/`delete`/`notification` 等产品词检索。
2. 过滤噪声（见下）。
3. 判定密度：**极高 / 高 / 中 / 低 / 极低（近乎零）**。
4. 若主体 ≈ 零产品吐槽：在报告开头写「主体变更 / 声量验证」段（对标 ALL Football 在小红书/X 的写法），主语改为**品类矩阵**，主体只收「个位数信号 + P0–P3 接收方」。

### 噪声过滤（按品类增补，默认剔除）

- 同名歧义（如 sport name ≠ App 名、美式橄榄球 vs 足球 App）
- 官方资讯转发、纯球员评分嘴炮
- 加密空投 / 积分活动噪音（如某 Club token）
- 机器人回复、纯营销种草无痛点

**有效吐槽定义**：明确指向某产品体验（广告、通知、付费、数据错误、卸载/迁移、UI），而非泛行业闲聊。

## Step 2 · 取数（X 默认）

用已连接的 **x** 命名空间（`GetDynamicTools` → `CallDynamicTool`）：

- `search_posts_all`：主工具；参数名是 `query` 不是 `q`；可用 `since:YYYY-MM-DD` 或 `start_time`；`sort_order` 先 `relevancy` 再补 `recency`；`max_results` ≤ 25。
- `get_posts_counts_recent`：近 7 日粗计（仅作「仍在爆发」旁证，不是全量）。
- `get_users_by_username`：解析官方号粉丝量级写入声量表。

注意速率：约 30 次/分钟、1000 次/日。查询分批并行，忌一次打爆。

### Query 设计套路

对每个竞品至少覆盖四类：

1. **痛点**：`(Brand OR @handle) (ads OR ad OR annoying OR delete OR trash OR unsubscribe OR unusable OR bug OR crash OR paywall OR notification OR spam)`
2. **迁移**：`Brand (moved OR switched OR deleted OR replace OR better) (CompetitorA OR CompetitorB)`
3. **品类高敏词**（按行业替换）：博彩/赌博广告、全屏广告、误触跳转、订阅逼迫等
4. **多语言**：西语 `publicidad|anuncios`、葡语 `anúncios` 等——命中密就开短节

把实际用过的 query 与命中概况写入报告附录。

## Step 3 · 编码证据

每条有效帖记入表格字段：

`# | 吐槽点（短标签） | 用户原话（原样照抄） | 证据强度 | 来源 URL`

### 证据强度

| 级 | 标准 |
|----|------|
| **强** | 独立账号 + 具体机制或**真实卸载/迁移行为**；或多语言重复出现 |
| **中** | 明确产品痛点但无迁移/无机制细节；或单条但行为清楚 |
| **弱** | 单条无细节、猜测、或疑同源传播 |
| **极强**（少用） | 用户用行动表达需求（开源替代客户端、长期维护的第三方纯净版等） |

优先把「有流失 + 写明 from→to」的簇放在报告最前（对标懂球帝「广告已造成真实流失」）。

聚类常见轴（按品类裁剪）：广告/变现侵入、误触与跳转、通知、数据/信任、付费与会员承诺是否兑现、稳定性、首页/个性化、迁移路径。

## Step 4 · 竞品三类对照

不要堆功能清单。固定三类视角（可增删，但须服务「对我方意味着什么」）：

1. **流失主因相关策略**（如广告/付费墙）
2. **核心频次体验**（如通知、打开路径）
3. **信任与差异**（数据口径、内容定位、场景被谁切走）

每类表格列：`竞品 | 用户怎么说 | 对分析主体/我方意味着什么`。

单独做一张 **迁移路径表**：`from → to | 原话 | 强度 | URL`，并写清主受益方 / 次受益方。

## Step 5 · 写出 P0–P3

| 优先 | 要求 |
|------|------|
| P0 | 有多条强证据或明确流失；不改会继续丢用户 |
| P1 | 刚需体验债（通知可控、口径可信等） |
| P2 | 个性化/场景定位 |
| P3 | 时效 SLA、区域替代雷达等 |

每行：`优先 | 方向 | 依据（引用条目 #） | 具体动作（可排期的 ①②③）`。

若主体无自身吐槽簇：**写明依据是品类级证据**，主体信号仅作同向确认——禁止假装「用户最恨我们的是 X」。

## Step 6 · 交付物结构（Markdown）

保存到 `/workspace/` 下清晰文件名，例如 `x_<subject>_complaints_YYYY-MM.md`，再把文件发给用户。章节顺序：

1. **题头表**：分析主体、矩阵、平台、时间窗、语言、报告日期（用户时区）
2. **先看这一条**：能证明什么 / 不能证明什么；有效吐槽定义；声量验证结论
3. **声量总览表**：各 App 密度 + 主痛点簇
4. **最要紧的一条**：主矛盾簇原话表 + 为何最值得重视
5. **迁移路径表**
6. **其余吐槽点**（分小节）
7. **竞品三类对照**
8. **多语言短节**（若有）
9. **可借鉴动作 P0–P3**
10. **边界与置信度**（高/中/低分级）
11. **附录：query 清单与命中概况**
12. **一句话结论（给产品）**

聊天回复：附件 + 一句话结论 + 迁移结构 + 主体声量一句 + P0 摘要。不要把全文贴进聊天。

用户若只要「一页评审版」：压缩为题头 + 主矛盾 5 条原话 + 迁移表 + P0 三条。

## Step 7 · 边界声明（每份报告必带）

- 来源：帖文正文（默认未做全量回复链、未交叉 App Store）
- 未覆盖：应用商店评论、私信、其它社交、DAU 级流失数据（除非本轮另取）
- 可用于：内部讨论、体验红线、广告/会员策略排期
- 不可用于：对外百分比宣称

## 与其它 skill 的边界

- 要做完整「我方 vs 竞品」战略报告 + 应对方案 → 用 `deep-competitor-analysis`，本 skill 的原话表可作其证据输入。
- 只要功能/定价对比矩阵 → `competitive-analysis-zh` / `ai-product-competitive-analysis`。
- 本 skill **只负责社交语料吐槽与借鉴初筛**，不替代装机实测与商店评论。

## 质量自检

- [ ] 每条原话能在工具结果里找到，且附 URL（或明确写无 URL）
- [ ] 无编造数字；粗计数标明 API/方法局限
- [ ] 声量近零时已改主语，未硬写吐槽簇
- [ ] P0 能追溯到强证据或迁移行为
- [ ] 开头与结尾都有边界/置信度
